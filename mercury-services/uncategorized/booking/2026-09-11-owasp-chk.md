## 2. Why the jackson-databind HIGH persisted (CVE-2026-68497)

CVE-2026-68497 (jackson-databind — *Allocation of Resources Without Limits*) is fixed
in the 2.21.x line at **2.21.6**. The booking jar shipped **2.21.4**, so it kept flagging.

**Why it wasn't picked up from commons:**
- commons `1.0.34-SNAPSHOT` uses Jackson **2.21.6**, but it **deliberately excludes
  `jackson-databind`** from its Jackson artifacts (`jackson-dataformat-csv`,
  `jackson-datatype-joda` both `<exclusion>` databind). So commons never dictates the
  databind version to consumers.
- `booking/pom.xml` has its **own** `dependencyManagement` importing `jackson-bom` at
  `${jackson.version}` = **2.21.4**. A module's own imported BOM takes precedence over
  versions arriving transitively through commons, so databind resolved to 2.21.4.

**Fix:** bump `booking/pom.xml` property `jackson.version` `2.21.4` → `2.21.6`
(matches commons; `jackson-bom` 2.21.6 is already in the local `.m2`). This forces every
Jackson module — including databind — to 2.21.6 and clears the CVE at the source.

### 2.1 What about the commons *parent* jackson-bom?

The `mercury-services-commons` **repo parent pom** DOES import `jackson-bom` 2.21.6 in its
`<dependencyManagement>` ("single source of truth for every com.fasterxml.jackson*"). But it
doesn't reach booking because:
- `dependencyManagement` is inherited only by Maven **children via `<parent>`**, so it governs
  only the commons repo's own modules (commons, cloud-sdk-*), not downstream consumers.
- booking's parent is `com.inttra.mercury:mercury-services:1.0` (the monorepo root), **not** the
  commons parent — so booking never inherits the commons jackson-bom.
- The published `commons` jar pom is flattened and carries no `<parent>`/`<dependencyManagement>`.
- The **mercury-services monorepo root pom** (booking's real parent) has **no** jackson-bom /
  dependencyManagement for Jackson, so nothing centrally governs Jackson for the services today.

**To centralize for the services:** add the jackson-bom import (or a published `mercury-bom`
import) to the **mercury-services root pom** `<dependencyManagement>` and remove each module's
local `jackson.version` pin. Then one change governs all service modules.

## 3. httpclient5 CVEs — suppressed to match visibility (ION-16792)

httpclient5 is pinned at **5.4.4** by commons (the 5.6.4 upgrade caused a gzip
double-decode in the Dropwizard Jersey client). The two CVEs affect code paths booking
does not use:
- **CVE-2026-71290** (CRITICAL) — ASYNC client TLS hostname verification bypass.
- **CVE-2026-40542** (HIGH) — SCRAM-SHA-256 mutual auth.

booking uses the CLASSIC (sync) httpclient5, so neither is reachable. Added the same two
`<suppress>` entries used by the visibility module to `booking/suppressions.xml`.

## 4. The other HIGH — t-digest 3.2 (CVE-2026-87822)

`com.tdunning:t-digest:3.2` — `MergingDigest.fromBytes` fails to validate centroid means
during deserialization, letting an attacker inject NaN centroids that degrade merge
sorting from O(n log n) to O(n^2) (DoS). Affects t-digest **3.1 through 3.3** (no fixed
release in that range), pulled in transitively (Elasticsearch/Lucene stack).

**Status:** open. Options: (a) suppress with justification if the deserialization path is
not exposed to untrusted input, or (b) exclude/upgrade the transitive t-digest once a
fixed version is published. Not changed in this pass — flagged for a decision.

## 5. Tooling finding — suppressions were not applied by owasp-scan-v2.ps1

The standalone `owasp-scan-v2.ps1` scanned the raw shaded jar **without** passing
`--suppression`, so module `suppressions.xml` files had no effect locally (only the
GitLab/CI dependency-check job applied them). Evidence: for the same module the CI report
`owasp-reports/visibility/visibility-s3-archiver/...` had CVE-2026-71290 suppressed,
while the v2-produced `owasp-reports/s3-archiver/...` still listed it.

`owasp-scan.ps1` / `owasp-scan.v1.ps1` do not support suppression either.

**Fix applied:** `owasp-scan-v2.ps1` now passes `--suppression <module>/suppressions.xml`
when the file exists, so the local scan matches the CI gate.

## 5a. commons now exports databind directly; pin-removal test

commons `1.0.34-SNAPSHOT` was updated to declare **`jackson-databind` 2.21.6 as a direct
dependency** (following the same "exclude + re-declare direct at safe version" pattern it
already uses for httpcore5/httpclient/gson). It now appears in the flattened commons POM and
wins nearest-wins for consumers that don't self-manage Jackson.

Tested removing booking's `jackson-bom` import: databind then **inherited 2.21.6 from commons**
(OWASP stayed `CRITICAL=0, HIGH=1`), **but** the rest of the Jackson family fragmented — old
transitive copies from **Elasticsearch 6.6.2** leaked in (`dataformat-yaml`/`smile` 2.8.11,
`cbor` 2.12.6, several artifacts 2.21.4). That is the exact risk the import prevents (mixing
databind 2.21.6 with dataformat 2.8.11 is a runtime-compat hazard).

**Decision: keep the `jackson-bom` import at 2.21.6.** It aligns the whole Jackson stack to
2.21.6 AND clears the databind CVE; commons' new direct databind is a consistent safety net.
Verified final state: all `com.fasterxml.jackson*` artifacts resolve to 2.21.6 (annotations
tracks the minor line at 2.21), build OK, OWASP `CRITICAL=0, HIGH=1` (t-digest only).
