## 1 Remove jsoup

We currently carry `jsoup` as a **direct compile dependency of `commons`** purely to satisfy a
**single test** in the `auth` module of the `mercury-services` repo. 
the cleanest remediation is to **remove jsoup entirely** rather than keep chasing versions.

**Fix in auth module:** exactly one test class transitively depends on jsoup —
`auth/.../idp/IdpServiceTest.java`. It must be rewritten to parse the SAML auto-POST form without
jsoup. 

| Item | State |
|---|---|
| jsoup used in `commons` production/test code | **No** — zero references |
| jsoup used in any `mercury-services` **application** code | **No** |
| jsoup used in `mercury-services` **test** code | **Yes — one class only** (`IdpServiceTest`) |
| jsoup declared directly by any `mercury-services` pom | **No** (was inherited transitively from `commons`) |

***

### 1.1 The one corrective change — rewrite `IdpServiceTest` 

jsoup is used **only** to extract hidden-input `name`/`value` pairs from a small, well-formed,
machine-generated HTML form. It does not need a full HTML5 parser.

### 1.2 Recommended rewrite (no new dependency)

Replace the jsoup parse with extraction that relies only on what is already on the `auth` test
classpath. Two acceptable options:

- **Option A (preferred) — regex over the hidden inputs.** The auto-POST form is generated by the
  OpenSAML `saml2-post-binding.vm` template with predictable `<input type="hidden" name="X"
  value="Y"/>` markup. A small regex that pulls `name` and `value` per `<input>` is robust for a
  test fixture and drags in nothing new. Sketch:

  ```java
  private static Map<String, String> extractHiddenInputs(String samlHtmlMessage) {
      Map<String, String> values = new HashMap<>();
      Matcher m = Pattern
          .compile("<input\\b[^>]*\\bname=\"([^\"]*)\"[^>]*\\bvalue=\"([^\"]*)\"",
                   Pattern.CASE_INSENSITIVE)
          .matcher(samlHtmlMessage);
      while (m.find()) {
          values.put(m.group(1), unescapeHtml(m.group(2)));
      }
      return values;
  }
  ```

  (Handle attribute order defensively if the template ever emits `value` before `name`; the
  current template emits `name` first. HTML-entity unescaping of the value can reuse the
  `commons-lang`/`commons-text` utilities already present, or the values are Base64/ASCII and need
  none.)

- **Option B — parse as XML with the JDK/OpenSAML XML stack already on the classpath.** The page
  is XHTML-ish; if it parses cleanly, a `DocumentBuilder` + XPath `//input` works. Slightly heavier
  and more brittle to non-XML HTML than Option A, so only if Option A is rejected in review.

After extraction, the remaining logic (Base64-decode `SAMLResponse`, unmarshal, assert) is
**unchanged** and jsoup-free.

## 2. httpclient5 — retain 5.4.4 in commons; do NOT upgrade to 5.6.4

> **Decision:** commons stays on **httpclient5 `5.4.4`** (with **httpcore5 `5.4.3`** / **httpcore5-h2
> `5.4.3`**). 
> The OWASP CVEs behind the `5.6.4` bump are **unreachable** on this stack and
> are handled by *suppression-with-justification*, not by upgrading. 
> Upgrading to `5.6.4` is a **known production regression** and must not be brought into commons.

### 2.1 Why 5.6.4 is unsafe — the gzip double-decode regression

httpclient5 **5.5+** rewrote content-compression handling. 
On **5.6.4** the transport-layer
`DecompressingEntity` **transparently gunzips** a `Content-Encoding: gzip` response **even when
Dropwizard calls `HttpClientBuilder.disableContentCompression(true)`** (which it does whenever
`jerseyClient.gzipEnabled=true`, the default). 

Dropwizard's Jersey `GZipDecoder` then runs a
**second** gunzip over already-plain JSON (bytes `5b 7b` = `[{`, not the gzip magic `1f 8b`),
throwing `java.util.zip.ZipException: Not in GZIP format`. 

On **5.4.4**, `disableContentCompression(true)`
is honoured, Jersey's `GZipDecoder` is the single decoder, and the body decodes exactly once.

### 2.2 Where it is already suppressed — git evidence (mercury-services)

Both affected reactors originally carried their **own** `httpclient5 = 5.6.4` pin, hit the production
failure, and fixed it by **removing that pin so the module falls back to the `5.4.4` that commons
pins**, adding a hermetic `GzipResponseDecodeTest` guard, and **suppressing** the two CVEs behind
5.6.4 with written justification:

| Commit | Author / date | Jira | What it did |
|---|---|---|---|
| `8abdb8d82f` | Arijit Kundu, 2026-09-03 | **ION-16417** | *"fix PISE_OUT gzip double-decode by reverting httpclient5 5.6.4 pin"* — reverts the pin in `partner-integrator/pom.xml`, adds `GzipResponseDecodeTest`, adds httpclient5 CVE suppressions to **7** pi modules |
| `e6e06773a6` | Sumesh Jacob, 2026-09-04 | **ION-16792** | *"Fix for double GZIP issue"* — removes the `5.6.4` pin from `visibility/pom.xml`, adds `GzipResponseDecodeTest`, adds the same suppressions to **10** visibility modules |
| `ecd27ab41d` | ION-16417 | — | clears remaining OWASP CRITICAL/HIGH in partner-integrator (httpclient5 / guava / gson / logback) |

The suppression text (identical wording in every `partner-integrator/*/suppressions.xml` under
ION-16417 and every `visibility/*/suppressions.xml` under ION-16792) reads:

> *"httpclient5 is kept at 5.4.4 (the version commons pins); the 5.6.4 upgrade caused a gzip
> double-decode in the Dropwizard Jersey client. Both CVEs behind that pin affect code paths
> partner-integrator does not use — CVE-2026-71290 is the ASYNC client TLS hostname verification
> bypass and CVE-2026-40542 is SCRAM-SHA-256 mutual auth. This service uses the CLASSIC (sync)
> httpclient5 with bearer-token auth, so neither is reachable."*

Each module suppresses exactly two vulnerabilities against
`pkg:maven/org.apache.httpcomponents.client5/httpclient5@.*`:

- **CVE-2026-71290** — CRITICAL (9.1) — **async** client TLS hostname-verification bypass (fixed 5.6.4).
- **CVE-2026-40542** — HIGH — **SCRAM-SHA-256** mutual-auth bypass (fixed 5.6.1).

### 2.3 ocean-schedules is not impacted — because of client wiring

The observation that the double-gzip issue "did not happen for ocean-schedules" is **true but for the
wrong reason**. 

Being hit requires **two** conditions together: (1) shipping httpclient5 5.6.4, **and**
(2) making calls through a **Dropwizard gzip-enabled Jersey client** (`JerseyClientModule` →
`gzipEnabled=true` + `GZipDecoder`) to a gzip-returning endpoint.

ocean-schedules fails condition (2): its outbound HTTP (`oceanschedules-process` collector `APIClient`
and the external carrier clients — MSC, CMA, Zim, Evergreen, Wisetech, etc.) uses **plain JAX-RS**
(`jakarta.ws.rs.client.WebTarget`, `ClientBuilder.newClient()`), **not** the commons Dropwizard gzip
path. With no Dropwizard `GZipDecoder` stacked on the transport there is no *second* decode, hence no
`ZipException`, regardless of httpclient5 version. 

This reflects a **different Dropwizard/JAX-RS client
initialization**, not its status as a non-AWS-upgraded module. The exemption is therefore
**module-specific and non-generalisable**: any ocean-schedules code path that later routes through the
commons Dropwizard gzip client against a gzip endpoint **would** be exposed if commons shipped 5.6.4.
It must not be used to justify a commons-wide 5.6.4 bump.

## 4. Jackson databind pin now actually reaches consumers

### 4.1 The gap

The `jackson-bom` import that pins `${jackson.version}=2.21.6` lives in the **root POM's
`<dependencyManagement>`**. `commons` flattens with `flatten-maven-plugin` in **default mode**, which
**strips `<dependencyManagement>`** from the published (flattened) POM. So the 2.21.6 pin governed
commons' *own* build but **never reached consumers** — they resolved `jackson-databind` transitively
via `commons → dropwizard-core → …` at the older Dropwizard-managed version. This is the same
"managed-only pin is stripped by flatten" trap already solved for `httpcore5` / `gson` / `jetty`,
which are re-declared as **direct deps** so they land in the flattened POM and win nearest-wins.
For `jackson-databind` only half the fix existed: databind was *excluded* from
`jackson-dataformat-csv` / `jackson-datatype-joda`, but never re-declared as a direct dep.

### 4.2 jackson trio

Re-declare the Jackson core trio as **direct deps** of `commons` (in `commons/pom.xml`, after
`jackson-dataformat-csv`):

```xml
<dependency><groupId>com.fasterxml.jackson.core</groupId><artifactId>jackson-databind</artifactId></dependency>
<dependency><groupId>com.fasterxml.jackson.core</groupId><artifactId>jackson-core</artifactId></dependency>
<dependency><groupId>com.fasterxml.jackson.core</groupId><artifactId>jackson-annotations</artifactId></dependency>
```

- **Versions are intentionally omitted** and inherited from the `jackson-bom` import. 
- `jackson-annotations` tracks its own version (`2.21`), which is exactly why the
  BOM maps each artifact separately. Omitting the version (mirroring the existing `jetty-server`
  direct-dep pattern) lets each artifact inherit its correct, coherent version, and flatten bakes the
  resolved value into the published POM.

### 4.3 Verification

- `mvn clean install` (full reactor): **BUILD SUCCESS, all tests pass**.
- The flattened published POM (`commons/flattened_pom.xml`) now carries, as **direct** deps at depth 1:
  `jackson-databind 2.21.6`, `jackson-core 2.21.6`, `jackson-annotations 2.21` — so nearest-wins hands
  2.21.6 to consumers that do **not** self-manage Jackson.

### 4.4 Caveat (unchanged from the assessment)

Consumers that import `jackson-bom` or pin Jackson in their own `<dependencyManagement>` (e.g.
`booking`, `visibility`) still **override** this.

`dependencyManagement` beats a transitive/direct dep regardless of depth. 
Those apps continue to manage Jackson themselves, as they have other jackson transitives which should be aligned for runtime consistency, so per-app bumps remain required.
This change is a safety-net default for unmanaged consumers, not a replacement for them.
