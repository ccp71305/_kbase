### Summary

The AppianWay platform ran **Dropwizard 4.0.16**, which transitively pins **Jetty 11.0.26** (end-of-life) and older Jackson/HttpComponents libraries, producing HIGH/CRITICAL OWASP Dependency-Check findings across **all 14 deployable modules** — a platform-wide CRITICAL (Jetty request-smuggling CVE-2026-2332) plus HIGH findings in jackson-databind and HttpComponents Core, and an outlier **`ingestor`** carrying **28 Netty CVEs** (two CVSS 10.0). Jetty 11.x is not available on the Dropwizard 4.x line, so the fix requires a **Dropwizard major upgrade to 5.0.2** (Jakarta EE10 / Jetty 12), applied by mirroring the versions already proven on `mercury-services-commons`. The remediation eliminated **all 19 CRITICALs and every real HIGH** (0 CRITICAL / 0 real HIGH across all 14 modules); the only residual is a **confirmed httpcore 4.x CPE false positive** pending a narrow Infosec-approved suppression. All 14 modules (18 run profiles) were then verified to **boot clean and resolve every AWS dependency** on the upgraded stack against the INT environment.

**Status:** ✅ Remediation complete on `feature/ION-16098-jetty-cve` (BUILD SUCCESS 22/22, 0 test failures); all 14 modules verified booting green against INT (2026-07-22). QA deploy pending.

## High Level Design

### Architectural Overview

AppianWay is a set of 14 deployable services (mostly SQS queue workers + a few gRPC/ES consumers) sharing a common Dropwizard/Jetty platform stack. The CVE exposure lives entirely in that shared platform layer, so the fix is centralized rather than per-service.

```
┌──────────────┐   ┌────────────────────────┐   ┌──────────────────────────┐   ┌───────────────────┐
│  AWS Trigger  │──▶│  Dropwizard App         │──▶│  Platform Libraries       │──▶│  AWS Services      │
│  SQS / gRPC   │   │  (Application + run cmd) │   │  Jetty / Jackson / HTTP   │   │  SQS SNS S3 DDB    │
│  DynamoDB     │   │  14 modules, 18 profiles │   │  ── the CVE surface ──    │   │  SSM (secrets)     │
└──────────────┘   └────────────────────────┘   └──────────────────────────┘   └───────────────────┘
                                                    Fix applies HERE (shared,
                                                    centralized in root pom DM)
```

### Data Flow — Before vs After

**Before (vulnerable):**
```
Dropwizard 4.0.16
  → transitively pins Jetty 11.0.26 (EOL)  → CVE-2026-2332 (CRIT 9.1), CVE-2026-5795 (HIGH)
  → jackson-databind 2.19.2/2.20.1         → CVE-2026-54512/54513 (HIGH)
  → httpcore5 5.3.4                         → CVE-2026-54399/54428 (HIGH)
  → ingestor bundles Netty 4.2.7.Final     → 28 CVEs (5 CRIT incl. two CVSS 10.0)
  → watermill-publisher drags plexus-utils  → CVE-2025-67030 (HIGH)
  = 19 CRITICAL + real HIGH across 14 modules
```
**After (fixed):**
```
Dropwizard 5.0.2 (Jakarta EE10)
  → Jetty 12.1.9 (jetty-bom + jetty-ee10-bom pin)   → both Jetty CVEs cleared
  → jackson-databind 2.21.4 (jackson-bom)           → cleared
  → httpcore5 5.4.3 (explicit pin)                  → real 5.x hit cleared
  → ingestor: dead ES transport client + Netty REMOVED → all 28 Netty CVEs gone at the root
  → watermill-publisher: stray jaxb2 plugin dep removed + jaxb-runtime 4.0.4 added → plexus-utils gone
  = 0 CRITICAL / 0 real HIGH; residual 2× httpcore 4.x = confirmed false positive
```

### httpcore 4.x false-positive provenance (why 2 HIGH remain)

CVE-2026-54399 / CVE-2026-54428 target **HttpComponents Core 5.x** (`httpcore5`, now pinned 5.4.3 = patched). Dependency-Check derives a CPE from jar evidence and matches the 5.x CVE's `apache/httpcomponents_core` product onto the **legacy `httpcore 4.4.16`** jars, whose version token is numerically below the 5.x bound → flagged. Provenance confirmed by `dependency:tree`:

| Artifact | Scope | Source chain |
|----------|-------|--------------|
| `httpcore:4.4.16` | Platform-wide (all 14) | AWS SDK 1.x: `aws-java-sdk-sqs → aws-java-sdk-core:1.12.720 → httpclient:4.5.14 → httpcore:4.4.16` |
| `httpcore-nio:4.4.16` | ingestor-only | Jest ES REST client: `io.searchbox:jest:6.3.1 → httpcore-nio:4.4.16` |
| `httpcore5(-h2):5.4.3` | Platform-wide | DW5 client: `dropwizard-client → httpclient5:5.6.1 → httpcore5:5.4.3` — **patched, not flagged** |

`4.4.16` is the terminal 4.x release (no upgrade exists). It cannot be isolated to one module — it enters everywhere via AWS SDK 1.x, and all ES traffic must be AWS-signed → removal requires an AWS SDK v2 migration (out of scope).

## Impact on Current Application

### Runtime Behavior

- All 14 modules (18 run profiles) boot cleanly on DW5 / Jetty 12.1.9 / Java 17 / Jackson 2.21.4 against INT with **no code or config change**.
- **Two benign platform-wide WARNs** appear on every module (logback-access version-expectation; AWS SDK v1 JAXB fallback) — cosmetic, pre-existing, non-blocking.

### Performance

No measurable regression. Startup times observed 500 ms–1.6 s across modules. AWS SDK v1 metrics behavior unchanged.

### Deployment

Standard rolling restart of each service on the upgraded fat jars. **No data migration, no config changes.** Requires the **Java 17** runtime (DW5/Jetty12/EE10). No coordinated cross-service deploy needed — modules deploy independently.

No failover/retry/circuit-breaker logic changed. Health-check registration is unchanged (some modules — distributor-rest, watermill-publisher, the 4 consumers — register no ops health check by design; verification for those is by boot evidence, see Deployment Verification).
