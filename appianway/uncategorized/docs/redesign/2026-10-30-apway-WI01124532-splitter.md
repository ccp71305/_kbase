## Summary

`splitter` consumes the `MetaData` envelope from its SQS pickup queue, reads the inbound document from the workspace bucket, parses it with the matching parser (EDIFACT, ANSI, rates, XML booking, CFAST, desktop; `gen2-parser` is a compile-time library with no AWS use and is unchanged), authorizes each transaction against Network Services, writes one child document per transaction or group back to the workspace bucket and routes each child `MetaData` to the queue mapped to its format's context code.

This change moves `splitter` off AWS SDK v1 onto `commons` + `cloud-sdk-api` + `cloud-sdk-aws` **1.0.38-SNAPSHOT** (AWS SDK 2.x) through `shared` re-based on commons: SQS, SNS and workspace S3 go through the `shared` Tier-2 adapters, SSM and client construction come from commons/cloud-sdk directly (Tier 1). Queue messages, events, stored objects, keys, character encoding and S3 headers are unchanged.

### Functional Requirements

1. Read the workspace document as ISO-8859-1 bytes decoded in full (no line joining), as today.
2. Write each split document to the workspace bucket under `{rootWorkflowId}/{uuid}` as ISO-8859-1 bytes with `Content-Type: application/octet-stream`; a single valid transaction keeps the original object (no write), as today.
3. Record the object size in the `SPLITTER_FILE_SIZE` projection from an S3 HEAD (no download), as today.
4. Send each enriched child `MetaData` (format id, integration-profile format id, context code, format code) to the routed queue; keep parallel group routing on the routing thread pool.
5. Keep event lineage, error codes and both error paths unchanged: batch-level failures re-queue the original body; per-transaction failures re-queue the split `MetaData`; `RecoveryConfig(true, 1, 150)` (one retry after 300 s, then `_dlq`).

### Non-Functional Requirements

1. No AWS SDK v1 API usage (`com.amazonaws` imports) in module sources.
2. Byte-for-byte wire compatibility of queue messages, events and stored objects (shared contract C1–C4, C7–C9).
3. Same worker concurrency (`maxNumberOfMessages`), routing thread pool size, long-poll wait and back-pressure receive as today.

### Acceptance Criteria

1. `mvn -pl splitter -am clean verify` is green.
2. Golden-fixture tests prove the child `MetaData`, retry `MetaData` and `Event` JSON are byte-identical to the v1 build.
3. Functional test proves split objects are byte-identical (ISO-8859-1, including non-ASCII characters) with `Content-Type` `application/octet-stream`.
4. Config golden test (program-level) passes for `splitter.yaml` with every environment's properties.
5. INT boot; a multi-transaction file produces the same child objects and messages as before.

## High Level Design

### Architectural Overview (ext)

```
 splitter pickup queue (SQS)
           │
           ▼
 shared back-pressure SQSListener ─▶ shared AsyncDispatcher (maxNumberOfMessages threads)
           │
           ▼
 SplitterTask ─▶ workspace adapter getContent (ISO-8859-1)
      │       ─▶ parser select / validate / split; Network Services authorization
      │       ─▶ routing pool (maxNumberOfMessages threads), per group:
      │            SplitTransactionProcessor ─▶ workspace adapter putObject(bytes) + getFileSize (HEAD)
      │                                     ─▶ FormatBasedSQSRouter ─▶ shared SQS sender (context queue)
      └───────▶ EventLogger ─▶ shared SNS EventPublisher (event topic)
           │
 failure ─▶ BatchErrorHandler (batch) / SplitErrorHandler (transaction) ─▶ retry / _dlq / errors queue
```

### Design Options Considered (ext)

| Option | Approach | Pros | Cons | Chosen |
|--------|----------|------|------|--------|
| 1 | Call cloud-sdk `StorageClient` / `MessagingClient` directly | Fewer layers | Bypasses the parity rules (HEAD size, empty objects, exception mapping, content type) | ❌ |
| 2 | `shared` Tier-2 workspace, SQS and SNS adapters with explicit charset and HEAD size | Keeps `WorkspaceService` contract, ISO-8859-1 and exception mapping | Adapter must reproduce v1 edge cases | ✅ |

### Data Flow — Before vs After (ext)

**Before:** v1 `AmazonSQS` receive → `shared` `S3WorkspaceService` (v1 `AmazonS3`) → `shared` `SQSClient` / `SNSEventPublisher` (v1) → `shared` `Json`.

**After:** `shared` back-pressure listener over `MessagingClient<String>` → `shared` workspace adapter (`StorageClient`, HEAD for size) → `shared` SQS sender / SNS `EventPublisher` (`MessagingClient<String>` / `NotificationService`) → `shared` `Json` (unchanged).

## Resiliency

Unchanged: failures map to the same `/exception/splitter/...` codes. Batch-level recoverable failures re-queue the original `MetaData` body; per-transaction recoverable failures re-queue the split `MetaData`; both with `failedAttempts` and `DelaySeconds` 300, then `_dlq` (max 1 attempt). Non-recoverable failures write annotations to the workspace bucket and post the `MetaData` to the errors queue before the message is deleted. S3/SQS/SNS cloud-sdk failures are mapped to `RecoverableException` by exception type in the `shared` adapters, as v1 `SdkClientException` was (shared C9). A batch-level retry re-splits and re-routes groups that were already sent (at-least-once, as today).

## Risks

**Key Risks**

- Character corruption if a UTF-8 default replaces ISO-8859-1 on read or write — mitigated by explicit charset in the module and adapter, and round-trip tests.
- Confusing `splitter`'s own `core.Message` with the SQS message type during retyping — mitigated by per-file changes and compile/tests.
- Retry counter loss if the receive does not request `failedAttempts` — mitigated by the `shared` listener and a retry-path test.
- Existing, unchanged: parallel group routing writes projections into the shared parent `MetaData` from several routing threads (`SplitTransactionProcessor.enrichMetaData`) while other threads copy it, so a child envelope can pick up another group's document control number. Golden tests run single-group fixtures; a fix is a separate change.
