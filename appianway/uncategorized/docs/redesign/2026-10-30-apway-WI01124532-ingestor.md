## Summary

`ingestor` is the AppianWay event indexer. It consumes SNS-wrapped lifecycle events from its queue (subscribed to the event topic), builds tracking attributes (Network Services lookups), loads error annotations from the workspace bucket for failed events, and writes event documents (bulk) and per-workflow aggregate upserts to daily Elasticsearch indices through Jest with AWS SigV4 request signing. Messages are always deleted after processing. A scheduled job purges expired indices.

This change moves the SQS, S3 and SSM interactions off AWS SDK v1 onto `commons` + `cloud-sdk-api` + `cloud-sdk-aws` **1.0.38-SNAPSHOT** (AWS SDK 2.x) through `shared` re-based on commons: SQS and workspace S3 go through the `shared` Tier-2 adapters, SSM and client construction come from commons/cloud-sdk directly (Tier 1). Elasticsearch access (Jest client, SigV4 signer, index layout, document format) is **unchanged**; the signer keeps using the v1 credentials provider chain, which commons 1.0.38 also uses for Jest.

### Functional Requirements

1. Consume from the existing queue with `listenerThreads` listeners, each receiving up to `maxNumberOfMessages` with the configured long-poll wait and processing the batch on the listener thread (module-local synchronous dispatcher); keep the always-delete behaviour.
2. Parse the SNS envelope and its `List<Event>` message exactly as today (`shared` `SNSNotification`, `Json`).
3. For failed `closeRun` events without annotations, read the annotations object from the workspace bucket via the `shared` workspace adapter `getContent(bucket, key)`; read failures are ignored, as today.
4. Keep the builders, Network Services enrichment and SSM-provided client credentials unchanged.
5. Index the same Elasticsearch documents: bulk event documents to `txtrack-event-yyyy-MM-dd` (type `event`) and aggregate upserts by workflow id to `txtrack-agg-yyyy-MM-dd` (type `aggregate`, `retry_on_conflict` 5); same JSON; same mapping templates and index purge.

### Non-Functional Requirements

1. No AWS SDK v1 API usage (`com.amazonaws` imports) in module sources, except the v1 credentials provider used by the Jest SigV4 signer in `JestModule`.
2. Byte-for-byte compatibility of Elasticsearch documents (see Backwards Compatible).
3. Same SSM parameter names and decryption.

### Acceptance Criteria

1. `mvn -pl ingestor -am clean verify` is green.
2. Golden-fixture tests prove event and aggregate documents are byte-identical to the v1 build.
3. `create-mapping-template` command still runs with the same CLI.
4. Config golden test (program-level) passes for `ingestor.yaml` with every environment's properties.
5. INT boot; a batch of events produces the same Elasticsearch documents as before, and messages are deleted.

## High Level Design

### Architectural Overview (ext)

```
 ingestor queue (SQS, subscribed to event topic)
          │
          ▼
 ListenerManager (module) ─▶ listenerThreads x shared back-pressure SQSListener
          │                    (asks the module AsyncDispatcher: always maxNumberOfMessages)
          ▼
 AsyncDispatcher (module, synchronous) ─▶ IngestorTask (whole batch on the listener thread)
   ├─▶ parse SNS envelope ─▶ List of Event        (shared Json)
   ├─▶ Builders ─▶ Network Services (credentials from SSM)
   ├─▶ ErrorTransformer ─▶ shared workspace adapter getContent(bucket, key)
   ├─▶ ElasticSearchEventRepository ─▶ Jest (SigV4 signer, v1 credentials chain; unchanged)
   └─▶ shared SQS client deleteMessage   (always, per message)
```

### Design Options Considered (ext)

| Option | Approach | Pros | Cons | Chosen |
|--------|----------|------|------|--------|
| 1 | Migrate SQS/S3/SSM via `shared`; keep `ingestor`'s Jest client and signer | No Elasticsearch behaviour change | v1 credentials classes stay on the classpath | ✅ |
| 2 | Use cloud-sdk `JestModule.newAwsSigningClient` | Less module code | Different timeouts and retries; logs access key id; still v1 credentials | ❌ (open issue 2) |
| 3 | Replace Jest with an OpenSearch client and SDK 2.x signing | Removes v1 from the module | New client and request model; out of scope | ❌ |

### Data Flow — Before vs After (ext)

**Before:** v1 `AmazonSQS` receive → `shared` `Json` parse → `S3WorkspaceService.getContent` (v1 `AmazonS3`) → builders → Jest index → v1 delete.

**After:** `shared` back-pressure listener over `MessagingClient<String>` → `shared` `Json` parse → `shared` workspace adapter `getContent` (`StorageClient`) → builders (unchanged) → Jest index (unchanged) → `shared` SQS client delete.

### Performance (ext)

No change in this program. Existing limit, kept as is: the Jest client uses Apache pool defaults (2 connections per route, 20 total) and 3 s connect/read timeouts, so the 8 listener threads share 2 connections to the Elasticsearch endpoint; each batch makes one bulk call plus one upsert per workflow. Tuning is a follow-up outside this program.

### Deployment (ext)

Rolling restart as part of the single AppianWay release. No re-index. A single service can be rolled back to its previous build alone, because formats are unchanged.

## Resiliency

Unchanged: Elasticsearch calls retry 3 times on exceptions (exponential wait from 100 ms); non-2xx/409 responses are only logged. Any exception in a batch (an unparsable message, or Elasticsearch still failing after retries) is logged and the whole batch is still deleted, so those events are not indexed. Event documents are indexed without ids, so a batch redelivered after a visibility timeout creates duplicate event documents (aggregates are idempotent upserts). These are existing behaviours, not changed by the SDK move; the `shared` adapters keep the v1 exception mapping (shared C9).

## Risks

**Key Risks**

- Document drift from a different `ObjectMapper` configuration — mitigated by keeping `shared` `Json` and golden-fixture tests.
- Signer library upgrade (0.0.16 → 0.0.22) changes signing — mitigated by INT signed-request check; fallback is pinning 0.0.16 in the module.
- AWS SDK v1 and 2.x on the same classpath (signer credentials; v1 transitive via `cloud-sdk-aws`) — different packages; one managed v1 version from commons.
- Existing, unchanged: one unparsable message (for example a plain-text `HEALTHCHECK` publish to the event topic, if delivered to this queue) or an Elasticsearch outage drops the whole received batch, because the batch is deleted after any failure.
