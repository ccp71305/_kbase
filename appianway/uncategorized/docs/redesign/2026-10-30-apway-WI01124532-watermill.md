## Summary

The Watermill consumers are gRPC stream consumers (`consumeForever`), not SQS listeners. Each one reads one Watermill topic from a start offset, turns each record into AppianWay output, keeps the last processed offset in memory and flushes it to the DynamoDB table `${environment}_watermill_offset`. On start or reconnect it resumes from the stored offset + 1, so delivery is at-least-once.

This page covers the platform:

- `consumer-commons`: offset entity, DAO, service, in-memory `OffsetUtil`, `OffsetUpdateScheduler`, `S3PublishService`, DynamoDB client support. All of the AWS SDK v1 code of the platform lives here.
- `consumer-framework`: generic flow `AbstractWatermillConsumerService`, `ConsumerConnectionFactory`, `AuthCredentials`, `OffsetManager`, retry. It has no AWS code of its own; it uses `shared` `ParameterSupplier` and the `consumer-commons` offset classes.
- `billoflading/ebl-inbound-consumers`, `billoflading/registration-inbound-consumers`: framework-based consumers that send each upsert to SQS.

The platform moves onto `shared` re-based on `commons` / `cloud-sdk` 1.0.38-SNAPSHOT (AWS SDK 2.x), see the `shared` page. DynamoDB uses the cloud-sdk enhanced repository directly (Tier 1); SQS and workspace S3 go through the `shared` Tier 2 adapters; SSM through the `shared` `ParameterSupplier` on `CloudParameterStore`. Offset rows, S3 objects and SQS messages stay byte-compatible. booking-inbound, visibility-inbound, cargoscreen and itv-gps have their own pages and take the new `consumer-commons` in the same release.

### Functional Requirements

1. Offsets in `${environment}_watermill_offset` behave exactly as today: read by `topicName` (eventually consistent); if absent, write `{topicName, offset=-1, readDateTime}` and consume from 0; otherwise consume from offset + 1.
2. Flushes as today: `OffsetUpdateScheduler` every `offsetUpdateDelay` minutes and on Dropwizard stop; `OffsetManager` on stream error (at most every 5 s) and when the consumer gives up. Each flush is an update of `offset` and `readDateTime` that leaves other attributes untouched.
3. `S3PublishService` writes the same bucket, key (`YYYYMMdd/<name>`) and body: UTF-8, `Content-Type: text/plain`.
4. EBL and Registration send each upsert of a `StructuredContentChangeEvent`, printed by protobuf `JsonFormat` (no insignificant whitespace), as one SQS message to the same queue: raw body, no attributes, no delay.
5. Watermill credentials are loaded once at startup from SSM (`GetParameters`, `WithDecryption=true`, same keys); an unknown name fails startup (C7). Every gRPC call carries `username`, `password`, `tenant`, `topic` metadata, as today.

### Non-Functional Requirements

1. No AWS SDK v1 API usage (`com.amazonaws` imports) and no `dynamo-client` in the platform modules or the two billoflading consumers.
2. Wire compatibility per the `shared` contract C1–C9 (C5 detailed below).
3. gRPC channel settings, reconnect and back-off unchanged.
4. Each module keeps its current test framework (JUnit 5 in these modules).

### Acceptance Criteria

1. `mvn -pl watermill/consumer-commons,watermill/consumer-framework,watermill/billoflading/ebl-inbound-consumers,watermill/billoflading/registration-inbound-consumers -am clean verify` is green.
2. DynamoDB-Local parity test: an item written by the v1 mapper is read by the v2 repository and vice versa; attributes `topicName` S, `offset` N, `readDateTime` N (epoch seconds), `writeDateTime` N (epoch seconds) when present.
3. `updateOffset` keeps attributes it does not set (for example an existing `writeDateTime`).
4. `S3PublishService` test: workspace adapter called with the same bucket and key; resulting request is UTF-8 with `Content-Type: text/plain`.
5. Config golden test (from the `shared` page) passes for both billoflading YAMLs with every environment's properties.
6. INT boot of EBL and Registration resumes from the stored offset with no gap and no reset.

## High Level Design

### Architectural Overview (ext)

```
 Watermill gRPC topic ──consumeForever(offsetStart)──▶ AbstractWatermillConsumerService (EBL, Registration)
                                                        │ handle(RawData): parse proto ─▶ JsonFormat
                                                        ▼
                                  shared SQS sender sendMessage(queueUrl, json)   (raw body, no attributes)
                                                        │ success
                                                        ▼
                                  OffsetManager.commitToMemory ─▶ OffsetUtil (in memory)
                                                        │
       OffsetUpdateScheduler (every offsetUpdateDelay min, on stop) / OffsetManager (onError, give-up)
                                                        ▼
       consumer-commons WatermillOffsetService ─▶ WatermillOffsetRepository (cloud-sdk enhanced repository)
                                                        ▼
                                          ${environment}_watermill_offset

 Other consumers: S3PublishService ─▶ shared workspace adapter putObject(String)  (UTF-8, text/plain)
 Credentials: shared ParameterSupplier ─▶ CloudParameterStore (GetParameters, decrypted) ─▶ AuthCredentials
```

### Design Options Considered (ext)

| Option | Approach | Pros | Cons | Chosen |
|--------|----------|------|------|--------|
| 1 | One v2 offset repository in `consumer-commons`; cargoscreen and itv-gps drop their duplicate DynamoDB classes | One implementation to test; entity verified wire-identical | cargoscreen changes imports | ✅ |
| 2 | Migrate each duplicate in place | Smallest diff per module | Three v2 copies of one contract | ❌ |
| 3 | `updateOffset` via repository `save` (`PutItem`) | Simple | Replaces the whole item; v1 used `UpdateItem` with null-skip | ❌ |
| 4 | `updateOffset` via repository `update` (`UpdateItem`, `IgnoreNullsMode.SCALAR_ONLY`) | Same as v1 `UPDATE_SKIP_NULL_ATTRIBUTES` | — | ✅ |
| 5 | `S3PublishService` calls cloud-sdk `StorageClient` directly | One layer less | Workspace bucket bypasses the `shared` adapter (program rule); `putObject(String)` on cloud-sdk sends `text/plain; charset=UTF-8` | ❌ |
| 6 | `S3PublishService` delegates to the `shared` workspace adapter `putObject(bucket, key, String)` | Parity (C2) and exception mapping (C9) in one place | — | ✅ |

### Data Flow — Before vs After (ext)

**Before:** v1 `AmazonDynamoDB` + `DynamoDBMapper` (table-name resolver `<environment>_watermill_offset`, default save behaviour) + `dynamo-client` `DynamoDBCrudRepository` (`findOne` → `load`, eventually consistent; `save` → mapper save with `UPDATE`; `update` → mapper save with `UPDATE_SKIP_NULL_ATTRIBUTES`). `S3PublishService` → v1 `AmazonS3.putObject(bucket, key, String)`. EBL/Registration → `shared` `SQSClient` on a v1 `amazonSQSForSender` client. `ParameterStoreModule` with a default v1 SSM client. `shared` `ConfigProcessingServerCommand`.

**After:** cloud-sdk `EnhancedDynamoRepository` for the offset (same table, item shape and operation types). `S3PublishService` → `shared` workspace adapter. EBL/Registration → the same `shared` `SQSClient` contract, bound by the `shared` v2 Guice module to `MessagingClient<String>`. `shared` `ParameterSupplier` on `CloudParameterStore`. Commons config chain. Consumer flow, gRPC and protobuf → JSON printing unchanged.

#### DynamoDB Changes (ext)

| Table | Partition Key | Sort Key | GSIs | Annotation Class |
|-------|--------------|----------|------|-----------------|
| `${environment}_watermill_offset` — **No change** | `topicName` (S) — No change | None | None | `consumer-commons` `WatermillOffset` (v1 `@DynamoDBTable` → v2 `@DynamoDbBean`) |

Attributes, no change: `offset` (N, Long; `-1` = no record processed yet), `readDateTime` (N, epoch seconds, written on every initialise and flush), `writeDateTime` (N, epoch seconds; modelled, never written by the consumers). The key is the configured `offsetKey`, defaulting to the topic name. No GSIs, no TTL attribute in use.

Client: commons defaults for DynamoDB (Tier 1): SDK default DynamoDB retry policy, `apiCallTimeout` 30 s from `DynamoDbClientConfig` (v1 had no overall timeout). Offset traffic is a few writes per flush interval, so no tuning is proposed.

#### Component Interaction Flow (ext)

```
 start / reconnect ─▶ OffsetManager.fetchNextOffset
            findById(key) ── present ─▶ start = offset + 1
                          └─ absent  ─▶ save {key, -1, readDateTime} ; start = 0
 record ─▶ handle ─▶ SQS / S3 ─▶ commitToMemory(offset)
 timer / stop / onError (≥5 s apart) ─▶ update {key, offset, readDateTime}   (UpdateItem, nulls skipped)
```

## Resiliency

Unchanged behaviour, recorded so the upgrade does not hide it:

- At-least-once. A crash replays everything since the last flush (up to `offsetUpdateDelay`, default 10 min). A graceful stop flushes in `OffsetUpdateScheduler.stop()` but does not stop the gRPC stream first, so records handled after that flush are replayed on the next start. EBL/Registration send several SQS messages per event; a failure part-way replays the whole event. Downstream consumers of these queues must tolerate duplicates.
- On reconnect, `fetchNextOffset` reads the row with an eventually consistent read just after the error-path flush; a stale read resumes earlier (duplicates, never a gap). Kept for parity.
- Connection errors reconnect forever with exponential back-off (`retryDelay` doubling, capped at 60 s); each attempt rebuilds the channel (`shutdown()` on the old one).

## Risks

**Key Risks**

- Offset regression (reset to 0 or skipped records) — mitigated by the parity IT, the update-semantics test and INT resume/rollback.
- Partition key mapped to `hashKey` instead of `topicName` would read every row as absent and reset to 0 — mitigated by the explicit `@DynamoDbAttribute("topicName")` and the parity IT.
- `PutItem` on update — mitigated by repository `update` (`UpdateItem`, null-skip).
- S3 header drift — mitigated by the workspace adapter and its C2 tests.
- Region resolution change on the DynamoDB client (open issue 5) — mitigated by defaulting to the SDK region provider chain.
- Existing, unchanged by this design (open issue 7):
  - `OffsetUpdateScheduler` uses `scheduleAtFixedRate`; `WatermillOffsetService.updateOffset` rethrows on a DynamoDB error, which ends all later periodic flushes until restart (`OffsetUpdateScheduler.java:38-49`, `WatermillOffsetService.java:40-42`). A later crash then replays from the last successful flush.
  - In `onError`, `flushIfChanged()` and `fetchNextOffset()` call DynamoDB before the reconnect is scheduled; an exception there leaves the consumer stopped with no reconnect (`AbstractWatermillConsumerService.java:227,237-247`).
  - `classifyError` treats only a `RuntimeException` with the "Message processing failed at offset" message as a processing error. With grpc-java, an exception thrown from `onNext` cancels the call and `onError` receives a `StatusRuntimeException` (CANCELLED), which is classified as a connection error, so `maxRetry` is likely never applied (`AbstractWatermillConsumerService.java:198,265-283`). Unit tests call `onError` directly and do not cover this; manual test 3 checks it.
  - `OffsetUtil.offset` is a non-volatile field written by the gRPC thread and read by the scheduler thread (`OffsetUtil.java:17`).
  - `S3PublishService` formats the folder with `YYYYMMdd` (week-based year), so the last days of December can land in the next year's folder (`S3PublishService.java:18`). Kept for key parity.
  - A null `offsetUpdateDelay` fails `OffsetUpdateScheduler.start()` (unboxing), although `OffsetDefinition` documents null as "flush on shutdown only"; the YAML default is 10.
