## Summary

Foundation of the AppianWay AWS SDK 2.x upgrade, released together with every module from one feature branch. The internal library `shared` (`com.inttra.mercury.shared:mercury-shared:1.0`) is **re-based on `mercury-services-commons` 1.0.38-SNAPSHOT** (`commons`, `cloud-sdk-api`, `cloud-sdk-aws`). It stops being a parallel platform with its own AWS clients, configuration loader and dependency stack, and becomes a thin AppianWay pipeline-runtime layer on top of commons:

1. Everything commons already provides — AWS clients and their tuning, retry policy, Parameter Store, the configuration transform chain, the exception model, resource lifecycle and third-party dependency versions — is taken from commons. The `shared` equivalents are deleted in the same release.
2. `shared` keeps thin adapters only where byte-level wire compatibility or AppianWay runtime behaviour requires them (S3 workspace, SQS sender and back-pressure listener, SNS event publisher, health checks).
3. AppianWay domain code (`MetaData`, `Event`, `Annotations`, `Json`, task / dispatcher / error-handler model, network services) stays in `shared` with the same packages and class names.

`functional-testing` gains cloud-sdk in-memory fakes; the root pom takes its platform versions from commons. All services switch to the new bindings in the same release.

### Functional Requirements

1. `shared` depends on `commons`, `cloud-sdk-api` and `cloud-sdk-aws` 1.0.38-SNAPSHOT and applies the three-tier boundary in High Level Design: use commons directly (Tier 1), thin parity adapter (Tier 2), AppianWay domain code unchanged (Tier 3).
2. Configuration is loaded through the commons transform chain (`PropertiesSubstitutionConfigProvider` → `TrimConfigCommentsTransform` → `ParameterStoreConfigTransform`) with the existing CLI `run (yaml) (properties...)`, YAML from the jar and `.properties` from the file system or S3. Resolved configuration is identical to today.
3. AWS clients are built with the cloud-sdk factories, one singleton per role, with the same timeouts, connection limits and retry profile as today's `AWSClientConfiguration`.
4. `shared` replaces the v1 `Message` signatures of the task, dispatcher, listener and error handler with SDK-neutral ones typed on the cloud-sdk `QueueMessage<String>`, and replaces the v1 bindings with a Guice module binding the cloud-sdk-based implementations. Every service binds it in the same release.
5. `shared`'s `pom.xml` declares no version for any library that commons manages; the root pom takes its platform versions (Dropwizard, Jetty, Jackson, logging, HTTP components, Guava) from commons.
6. `functional-testing` offers in-memory cloud-sdk fakes (queue, storage, notification, parameter store) and assertions, plus an injectable server command for `IntegrationTestSupport`. The v1 fakes are removed with the v1 code (build step 5).

### Non-Functional Requirements

1. No AWS SDK v1 API usage (`com.amazonaws` imports) in `shared` once the v1 code is removed (build step 5).
2. Package names and the Tier 3 domain classes are kept. v1-typed entry points, wrappers, bindings and test fakes are removed in the same release, so no AWS SDK v1 API remains in `shared`.
3. Same throughput and latency profile: back-pressure listener, same client timeouts and pool sizes, no whole-object downloads where today only metadata or size is read.
4. New test classes use JUnit 5 (Jupiter). Existing JUnit 4 tests run unchanged on the JUnit Vintage engine; no class mixes both. JUnit Platform versions come from the JUnit BOM managed by Dropwizard (no version pins).

### Acceptance Criteria

1. `mvn clean verify` is green for the whole reactor at every build step.
2. Golden-fixture tests prove that the v2 SNS publisher and SQS sender emit bodies byte-identical to the v1 publishers and senders for `MetaData`, `Event` (with and without annotations or tokens, and with null or empty fields) and `List[Event]`.
3. Adapter tests (mocked cloud-sdk clients) assert the exact request shape for each contract item: S3 content type, metadata and copy directive; SQS attributes and delay; SNS plain publish; SSM decryption.
4. Config golden test: for every module YAML and every environment's `.properties` set in the repository, the text resolved by the commons chain equals the text resolved by today's `shared` command (comment lines excluded).
5. Dependency check: `mvn dependency:tree` for every service shows the commons-managed versions for Dropwizard, Jetty, Jackson, logging and HTTP components (no downgrade by AppianWay pins).
6. Source check: `shared` contains no `com.amazonaws` imports once the v1 code is removed (test 9).
7. Test-count check: each module's Surefire test count equals its previous count plus the new tests, so no JUnit 4 test is silently skipped after the switch to the JUnit Platform.

## High Level Design

### Architectural Overview (ext)

```
         BEFORE                                         AFTER (per migrated module)
 service                                         service
   │                                               │
   ▼                                               ▼
 shared                                          shared (AppianWay pipeline runtime)
   own AWS clients (SDK v1)                        Tier 3: MetaData, Event, Annotations, Json,
   own config loader                                       task / dispatcher / ErrorHandler,
   own dependency versions                                 network services (unchanged)
   ─▶ AWS SDK v1                                   Tier 2: workspace, SQS sender, back-pressure listener,
                                                           SNS event publisher, health checks (thin adapters)
                                                       │
                                                       ▼
                                                 commons ─ config chain, platform dependency versions
                                                 cloud-sdk-api / cloud-sdk-aws (Tier 1)
                                                   MessagingClient, StorageClient, NotificationService,
                                                   CloudParameterStore, client factories, retry, exceptions
                                                       │
                                                       ▼
                                                 AWS SDK 2.x

 shared v1 code: removed in the same release
```

### Three-Tier Boundary (ext)

| Tier | Rule | Contents |
|------|------|----------|
| 1 — commons | Use commons / cloud-sdk directly; the `shared` equivalent is deleted in the same release | AWS client construction and HTTP tuning, retry condition, credentials and region, Parameter Store, DynamoDB, SES, exception model, `CloudResource` lifecycle, configuration transform chain, third-party dependency versions |
| 2 — thin adapter | `shared` keeps a small adapter over a cloud-sdk interface because the wire format or runtime behaviour must stay identical | S3 workspace, SQS sender, back-pressure SQS listener, SNS event publisher, health checks, S3 configuration source, cloud-sdk → `RecoverableException` mapping |
| 3 — AppianWay domain | Unchanged in `shared` | `MetaData`, `Event`, `Annotations`, `Json`, `EventLogger`, task / dispatcher / error-handler model, network services, structural validation, XML helpers, `MailContext`, external-call wrapper |

Services use the Tier 2 adapters for every SQS, SNS and workspace-S3 operation that `shared` wraps today. Direct cloud-sdk use in a service is limited to capabilities `shared` does not wrap (DynamoDB, SES, module-specific buckets), and each module design states the call and the compatibility rule.

**AWS SDK boundary:** No AWS SDK client is built or called directly in AppianWay code. Module and `shared` code depend only on the `cloud-sdk-api` interfaces (`MessagingClient`, `StorageClient`, `NotificationService`, `DatabaseRepository`, `CloudParameterStore`, `EmailService`). Their implementations are created only by the `cloud-sdk-aws` factories, in Guice wiring (the `shared` v2 module, or a module's `ExternalServicesModule` for DynamoDB and SES). The only AWS SDK types allowed, as in mercury-services, are: SDK configuration values passed to the factories inside the `shared` client-profile helper (`RetryStrategy`, the CloudWatch metric publisher); SDK clients built by that helper with the same profile, only when a module sets a CloudWatch metrics namespace (transformer, `shared` open issue 13), wrapped in the public `cloud-sdk-aws` implementations; DynamoDB enhanced-client entity annotations; catching `ConditionalCheckFailedException` for version conflicts (U10); and the v1 credentials provider of the Elasticsearch SigV4 signer, which the `cloud-sdk-api` `JestClientBuilder` itself requires (ingestor). An architecture test enforces this (open issue 14).

### Backward-Compatibility Contract (ext)

The `shared` adapters enforce these rules for every module that migrates onto them:

| # | Area | Rule |
|---|------|------|
| C1 | JSON | Services keep `shared`'s own `MetaData`, `Event` and `Annotations`, serialized with `shared` `Json` (unchanged). Never use cloud `JsonSupport` for wire output: it registers `Jdk8Module`, sets global `NON_NULL`, writes `LocalDateTime` fields without `@JsonFormat` as ISO strings instead of arrays and reads unknown enum values as null |
| C2 | S3 | String put: UTF-8 bytes with `Content-Type: text/plain` (cloud-sdk `putObject(String)` would send `text/plain; charset=UTF-8`). Byte put: `application/octet-stream`. Empty objects can be written. User metadata keys are preserved and trimmed as today; metadata returned to callers is a mutable, case-insensitive copy. Copy with metadata uses REPLACE and passes `application/octet-stream` explicitly (SDK v1 adds that header to every request without one, so today's REPLACE copies store it; an SDK 2.x request without it would store `binary/octet-stream`); plain copy uses COPY. A copy that cloud-sdk reports as failed (`copyObject` returns false) raises `RecoverableException`. No SSE or ACL is set. Reads decode as UTF-8. `getContent(bucket,key)` keeps the line-joining behaviour. File size uses HEAD, not a download. Copy to file streams to disk. A missing key raises `RecoverableException`, as today |
| C3 | SQS | Same queue URLs and raw body. Receive: long poll 20 s (or configured), at most the dispatcher's idle-permit count, `messageAttributeNames=[failedAttempts]`, no visibility timeout in the request (queue default, as today). Retry send: String attribute `failedAttempts` plus `DelaySeconds = 2^attempt × delayMultiplier` |
| C4 | SNS | Same topic and raw JSON (events published as a JSON array via `shared` `Json`). No subject, message attributes or message structure |
| C5 | DynamoDB | Same tables, attribute names and types (details in the module designs) |
| C6 | SES | Same sender, recipients and rendered body (details in the module designs) |
| C7 | SSM | Same parameter names, `WithDecryption=true`, no value transformations. An unknown name fails startup, as today |
| C8 | Config | YAML keys and `.properties` unchanged. Environment first, then properties; `${key:-default}` supported; an unresolved placeholder fails startup. CLI `run (yaml) (properties...)`. `${awsps:...}` placeholders become available but none are introduced by this program |
| C9 | Exceptions | Wherever the v1 wrappers wrapped an SDK failure in `RecoverableException` (`SQSClient` wraps every `SdkClientException`), the adapter wraps the cloud-sdk failure the same way, by exception type (`CloudSdkException` subtypes and the storage and parameter-store runtime exceptions). `isRetryable()` is logged but does not narrow today's behaviour |

### Design Options Considered (ext)

| Option | Approach | Pros | Cons | Chosen |
|--------|----------|------|------|--------|
| 1 | Keep `shared` as a parallel platform: add SDK 2.x adapters but keep its own client builders, config loader and dependency versions | Least change to `shared` | AppianWay keeps maintaining its own dependency stack and config loader separately from mercury-services | ❌ |
| 2 | Retire `shared`; services call commons / cloud-sdk directly | Maximum alignment | Not wire-identical (cloud `JsonSupport`, `SnsEventPublisher`, network-service models); cloud-sdk listener has no back-pressure; task and error model rewritten in every service | ❌ |
| 3 | New AppianWay foundation module, retire `shared` | Clean break | Package churn in every service; two foundation libraries during transition | ❌ |
| 4 | Re-base `shared` on commons with the three-tier boundary; upstream generic gaps (U1–U4) to commons | One platform and dependency stack with mercury-services; wire parity enforced in one place; no package churn | Small upstream asks; every service migrates in the same release | ✅ |

### Data Flow — Before vs After (ext)

**Before:** service → `shared` v1 wrapper (`SQSClient`, `SNSClient`, `S3WorkspaceService`, `ParameterStore`) → SDK v1 client built inline with `AWSClientConfiguration`.

**After:** service → `shared` Tier 2 adapter (same method contract) → cloud-sdk `MessagingClient<String>` / `NotificationService` / `StorageClient` / `CloudParameterStore` built by the cloud-sdk factories → SDK 2.x. Messages, objects and events on the wire are unchanged.

#### Client Profile (ext)

One client per role, built once by the cloud-sdk factories and closed by the Dropwizard lifecycle (`ManagedCloudResource`). Defaults reproduce today's `AWSClientConfiguration`; a module whose current clients differ passes overrides, stated in its design:

| Role | Connect | Socket | API-call timeout | Max connections | Retries | Backoff | Retry condition |
|------|---------|--------|------------------|-----------------|---------|---------|-----------------|
| SQS listener | 1 s | 30 s (must exceed the 20 s long poll) | none | 50 | 3 | exponential 500 ms – 5 s | cloud-sdk `AwsRetryCondition` (retries every failure, as today) |
| SQS sender | 1 s | 5 s | 10 s | 50 | 3 | same | same |
| S3 | 1 s | 5 s | none (see note) | 50 | 3 | same | same |
| SNS | 1 s | 5 s | 10 s | 50 | 2 | same | same |

Notes:

- S3: the v1 10 s client-execution timeout ended when the response arrived and did not cover reading a streamed body. An SDK 2.x API-call timeout also covers reading the body, and cloud-sdk `getContent` / `getObject` read it fully, so a 10 s cap would fail large documents that work today. The S3 client therefore sets no API-call timeout; stalled transfers are bounded by the 5 s socket timeout.
- DynamoDB clients (module designs) do not use `AwsRetryCondition`: retrying every failure would resend conditional writes that failed on version conflicts. They use the SDK standard retry strategy, as v1 `DynamoDBMapper` did.
- Metrics: a module that sets a CloudWatch metrics namespace (transformer) gets every client built with the same profile plus one shared `CloudWatchMetricPublisher` (open issue 13).

#### Guice Module Loading Order (ext)

Every service installs the `shared` v2 module in place of its v1 `ExternalServicesModule` bindings; module-specific bindings (DynamoDB, SES) come after it.

- Listener back-pressure is kept: a service never holds more received messages than it has idle workers, so messages are not left waiting until their visibility timeout expires.
- Clients are singletons per role with the same pool sizes; health checks reuse them instead of creating extra clients and connection pools.
- Size lookups use HEAD; copy-to-file and large puts stream to or from disk.
- SDK 2.x clients start slower than v1 on first use; each service creates its clients at startup so the first message does not pay the cost.

### Deployment (ext)

Released together with every module. `shared` is a library and has no deployment of its own.

---

## Resiliency

Keeps the current model: transient failures raise `RecoverableException`, and the service's `ErrorHandler` re-queues with `failedAttempts` and `DelaySeconds = 2^attempt × delayMultiplier` (defaults: 5 attempts, multiplier 10, maximum 320 s), or routes to the DLQ or errors queue, then deletes the original. AWS client retries and backoff match today's per-role profile. The external-call wrapper (Hystrix and guava-retrying) is unchanged.

## Risks

**Key Risks**

- Silent wire drift if a module bypasses the `shared` adapters. Mitigation: module designs require the adapters; golden tests run for every module.
- cloud-sdk behaviour that differs from SDK v1 (empty-object rejection, `copyObject` returning false instead of throwing, `putObject(String)` content type, different HTTP defaults). Mitigation: handled in the adapters, covered by tests 2, 3 and 8.
