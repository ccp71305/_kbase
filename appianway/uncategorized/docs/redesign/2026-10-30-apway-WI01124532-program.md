## Summary

AppianWay is the event-driven file-processing layer: it ingests partner and carrier messages, validates and transforms them to the canonical model, delivers outbound documents and emits lineage events. All services and the Watermill consumers use AWS SDK v1 (1.12.720), mostly through the internal library `mercury-shared`.

This program moves every AppianWay service to `commons` + `cloud-sdk-api` + `cloud-sdk-aws` **1.0.38-SNAPSHOT** (AWS SDK 2.x), in one release built on one branch. The internal library `shared` is **re-based on commons**: AWS clients, client tuning, Parameter Store, configuration loading, the exception model and third-party dependency versions come from commons, so AppianWay runs on the same platform stack as mercury-services; `shared` keeps only thin wire-compatibility adapters and the AppianWay pipeline runtime (task, dispatcher, error handling, `MetaData` / `Event` / `Json`). All data formats produced or consumed by AppianWay — SQS/SNS message bodies, S3 objects, DynamoDB items, emails — stay byte-compatible. This page holds the shared design; each module has its own page.

### Functional Requirements

1. Every service keeps its current behaviour: same queues, topics, buckets, tables, keys and payloads.
2. AWS access goes through `cloud-sdk-api` interfaces (`MessagingClient`, `NotificationService`, `StorageClient`, `ParameterStore`, email and database APIs) implemented by `cloud-sdk-aws`.
3. `shared` follows a three-tier boundary (see the `shared` design): Tier 1 — taken from commons / cloud-sdk directly (AWS clients and tuning, retry, Parameter Store, DynamoDB, SES, exceptions, lifecycle, configuration chain, dependency versions); Tier 2 — thin `shared` adapters where wire or runtime parity needs them (S3 workspace, SQS sender, back-pressure listener, SNS event publisher, health checks); Tier 3 — AppianWay domain code unchanged (task / dispatcher / error model, `MetaData` / `Event` / `Annotations` / `Json`, network services). All services switch to the new bindings in the same release.
4. Configuration is loaded through the commons transform chain with the existing CLI, YAML and `.properties` files; the resolved configuration is identical to today.
5. Services use the `shared` adapters for every SQS, SNS and workspace-S3 operation `shared` wraps today; direct cloud-sdk use is limited to DynamoDB, SES and module-specific buckets.
6. No AWS SDK client is built or called directly in AppianWay code. Module and `shared` code depend only on the `cloud-sdk-api` interfaces (`MessagingClient`, `StorageClient`, `NotificationService`, `DatabaseRepository`, `CloudParameterStore`, `EmailService`). Their implementations are created only by the `cloud-sdk-aws` factories, in Guice wiring (the `shared` v2 module, or a module's `ExternalServicesModule` for DynamoDB and SES). The only AWS SDK types allowed, as in mercury-services, are: SDK configuration values passed to the factories inside the `shared` client-profile helper (`RetryStrategy`, the CloudWatch metric publisher); SDK clients built by that helper with the same profile, only when a module sets a CloudWatch metrics namespace (transformer, `shared` open issue 13), wrapped in the public `cloud-sdk-aws` implementations; DynamoDB enhanced-client entity annotations; catching `ConditionalCheckFailedException` for version conflicts (U10); and the v1 credentials provider of the Elasticsearch SigV4 signer, which the `cloud-sdk-api` `JestClientBuilder` itself requires (ingestor). An architecture test enforces this (Acceptance Criteria).

### Non-Functional Requirements

1. No AWS SDK v1 API usage (`com.amazonaws` imports) in the sources of a migrated module.
2. Backward compatibility of every wire and storage format (see Backwards Compatible).
3. All modules are released together from one feature branch. Wire and storage formats stay identical, so any single service can still be rolled back to its previous build without breaking the flow (dispatcher → splitter → transformer → mercury-services → transformer → distributor).
4. Same throughput and latency profile: back-pressure SQS listener, per-role client timeouts and pool sizes as today, no whole-object downloads for size or metadata reads.
5. Third-party library versions are managed by commons; AppianWay does not pin a platform library below the commons-managed version.

### Acceptance Criteria

1. `mvn clean verify` green for every step on the branch.
2. Golden-fixture tests prove byte-identical JSON for `MetaData`, `Event` and every module-specific payload.
3. A config golden test proves identical resolved configuration for every module and environment.
4. An architecture test (ArchUnit, test scope, in `functional-testing` and run by every migrated module) fails the build on any `software.amazon.awssdk` client, request or builder type, or any `com.amazonaws` type, outside the allowed list in Functional Requirement 6.
4. DynamoDB-Local parity tests prove items written by v1 are read and updated by v2, and vice versa.
5. INT verification per module before promotion.

## High Level Design

### Architectural Overview (ext)

```
          BEFORE                                         AFTER
  service ─▶ shared (own clients,               service ─▶ shared (pipeline runtime + thin adapters)
            own config loader,                                   │
            own dependency versions)                             ▼
            ─▶ AWS SDK v1                                  commons (config chain, dependency versions)
                                                           cloud-sdk-api / cloud-sdk-aws ─▶ AWS SDK 2.x
```

`shared` keeps the AppianWay concurrency and error model and its `MetaData` / `Event` / `Json` (wire format unchanged by construction); `cloud-sdk` provides the AWS clients, their tuning and the exception model; `commons` provides configuration loading and the platform dependency stack, so library upgrades made in commons reach AppianWay through a version bump. The cloud-sdk-api workflow types are field-identical to `shared`'s; convergence is out of scope.

### Design Options Considered (ext)

| Option | Approach | Pros | Cons | Chosen |
|--------|----------|------|------|--------|
| 1 | Re-implement `shared` wrappers on AWS SDK 2.x without cloud-sdk | Smallest code change | Duplicates cloud-sdk; second v2 stack to maintain | ❌ |
| 2 | Keep `shared` as a parallel platform with cloud-sdk adapters but its own client builders, config loader and dependency versions | Least change to `shared` | AppianWay keeps maintaining a separate dependency stack and config loader | ❌ |
| 2a | Retire `shared`; services call commons / cloud-sdk directly | Maximum alignment | Not wire-identical (JSON mapper, event publisher, network-service models); no listener back-pressure; task model rewritten in every service | ❌ |
| 2b | Re-base `shared` on commons (three tiers); all services switch in one release; v1 code removed in the same release | One platform and dependency stack with mercury-services; wire parity enforced in one place; no package churn; no v1 code left in `shared`; one end-to-end test cycle; per-service rollback still possible | Commons U3 and U8–U9 must be released first; one larger release to test | ✅ |
| 3 | New separate AppianWay foundation module, retire `shared` | Clean break from v1 | Package churn in every service; two foundation libraries during transition | ❌ |
| 4 | Release wave by wave, v1 and v2 services side by side for several releases | Smaller releases | `shared` carries v1 and v2 code until the last wave; the whole flow is re-tested after every wave | ❌ |

### Data Flow — Before vs After (ext)

Unchanged end to end. Only the client library under each AWS call changes:

```
inbound file ─▶ dispatcher ─▶ splitter ─▶ transformer ─▶ distributor / distributor-rest
                    │             │             │                 │
                    └─────────────┴──── lineage events (SNS) ─────┴──▶ event-writer, ingestor
failures ─▶ errors queue ─▶ error-processor ─▶ email-sender
Watermill gRPC streams ─▶ watermill consumers ─▶ S3 / SQS / SNS ;  watermill-publisher ─▶ Watermill
```

## Low Level Design

### Server

#### Key Components and Changes (ext)

| # | Component | Key Changes |
|---|-----------|-------------|
| 1 | `shared` (re-based on commons) | Tier 1 items taken from commons / cloud-sdk; Tier 2 adapters (workspace, SQS sender, back-pressure listener, SNS event publisher, health checks, exception mapping) and a v2 Guice module; Tier 3 domain code unchanged; v1 wrappers removed |

#### Release and Build Order (ext)

All modules are built on one feature branch, merged to `develop` once and released together. Prerequisite: a commons release containing U3 and U8–U9 (Open Issue 2). Build order on the feature branch, each step keeping the full reactor build green:

| Step | Modules |
|------|---------|
| 1 | `shared` (re-base on commons), `functional-testing`, root pom (commons version, platform pins aligned) |
| 2 | event-writer, error-processor, email-sender |
| 3 | dispatcher, splitter, transformer, distributor, distributor-rest, ingestor |
| 4 | watermill-publisher, Watermill consumer platform and consumers |
| 5 | Remove the AWS SDK v1 code from `shared` and the v1 test fakes |

## Resiliency

Unchanged semantics. AWS failures that were `RecoverableException` under v1 stay recoverable: the `shared` adapters map cloud-sdk failures by exception type (not only `CloudSdkException.isRetryable`) to the existing retry path; non-recoverable failures follow the existing `ErrorHandler` flow (failure event, errors queue, delete).

## Backwards Compatible

**Yes.** The following rules apply to every module:

| # | Area | Rule |
|---|------|------|
| C1 | JSON | Services keep `shared`'s own `MetaData` / `Event` / `Annotations`, serialised with `shared` `Json` (never cloud `JsonSupport`); golden-fixture tests |
| C2 | S3 | Same buckets and keys; text objects keep `Content-Type: text/plain` with UTF-8 bodies; binary objects keep `application/octet-stream`; user metadata keys unchanged; copy semantics unchanged; no new encryption or ACL settings |
| C3 | SQS | Same queues and raw bodies; retry attribute `failedAttempts` and delay behaviour unchanged |
| C4 | SNS | Same topics; raw JSON body; no subject or message attributes added |
| C5 | DynamoDB | Same tables, keys, attribute names and types, including epoch-second dates and optimistic-lock versions |
| C6 | SES / SSM | Same sender, reply-to and charset; same parameter names with decryption |
| C7 | Config | Same YAML keys and override files |

## Risks

**Key Risks**

- JSON output drift from mapper configuration — mitigated by rule C1 and golden fixtures.
- DynamoDB attribute or version drift — mitigated by rule C5 and DynamoDB-Local parity tests.
- Model JSON drift from the AWS SDK 2.x booking/visibility models — mitigated by excluding exactly the new properties and by golden fixtures.
- Configuration resolving differently under the commons chain — mitigated by the config golden test.
