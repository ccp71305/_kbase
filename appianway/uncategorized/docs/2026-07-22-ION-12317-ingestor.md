# ingestor — AWS SDK v2 (cloud-sdk) Upgrade Design

> Module: `ingestor` · Main: `com.inttra.mercury.ingestor.IngestorApplication` · Port 8081 · Part of the ION-12317 AppianWay AWS SDK v2 upgrade program.
> **Shared foundation** (mapping, slim `appianway-commons`, config/SSM model, cloud-sdk gaps S-G2/W-G9/X-G7/X-G8, Maven template, rollout) lives on the program page — this page adds only ingestor's module-specific detail.
> **Baseline (unchanged):** Dropwizard 5.0.2 / Jetty 12.1.9 / Java 17 / Jackson 2.21.4 (ION-16098, in `develop`). Both `ingestor` and `ce-ingestor` boot clean on that stack today (still on AWS v1 + `shared` + a local v1-credentialed Jest signer).

## 1. Overview

ingestor is the **event-indexing sink** of the appianway pipeline (despite the name, not a first-stage receiver): it consumes `Event`/`SNSNotification` payloads fanned onto its inbound SQS queue, enriches them with `TrackingMetaData` via a chain of `Builders`/`AttributeBuilder`s, resolves error content from S3 when needed, and bulk-indexes the result into an AWS-managed **Elasticsearch (OpenSearch)** domain via the **Jest** (`io.searchbox`) REST client, which it AWS-signs itself. A `wisp` scheduler runs a 24-hourly job that deletes expired daily indices.

- **Current state (DW5 baseline):** AWS Java SDK **v1 (1.12.720)** + `shared` for SQS/S3/config/health/network-services, and a **local v1-credentialed Jest signer**. Boots clean on INT (both profiles).
- **Target:** `commons` + `cloud-sdk-api` + `cloud-sdk-aws` (`1.0.27-SNAPSHOT`) + slim `appianway-commons`. `shared` deleted from the dependency tree.
- **Headline change (X-G8) — corrected:** ingestor is the **only** one of the 14 modules that AWS-signs a *non-AWS-native* HTTP call (Elasticsearch/Jest) with AWS credentials. **AWS SDK v2 is not compatible with the Jest (`io.searchbox` 6.3.1, Apache HttpClient 4.x) + `vc.inreach.aws.request.AWSSigner` (v1 SigV4) stack, and no module in mercury-services migrates that signer to v2** — verified against `visibility-inbound` (v1 `AWS4Signer` + copied interceptor), `oceanschedules` (loader/port-pair-generator: `vc.inreach` `AWSSigner` + `AWSSigningRequestInterceptor`), and the `elasticsearch-purge` lambda (v1 `AWS4Signer`). So the module-specific piece is the **opposite** of a v2 migration: **keep Jest + the `vc.inreach` v1 signer exactly as-is** while everything else moves to cloud-sdk v2 — which means ingestor **retains `vc.inreach:aws-signing-request-interceptor` and a minimal AWS SDK v1 auth/credentials jar** on its classpath, coexisting with the cloud-sdk-aws v2 stack. Everything else is the standard SQS/S3-read/network-services rebind of the light consumers.
- **Two deployments, one jar:** `ingestor` (queue `inttra_int_sqs_ingest`) and `ce-ingestor` (queue `inttra_int_sqs_ingestor_ce`) — same `ingestor-1.0.jar`/`ingestor.yaml`, different first `.properties`. No profile-specific AWS surface differences beyond the queue URL.

## 2. Current vs Target architecture

```
BEFORE — ingestor on shared + AWS v1
  IngestorApplication ─▶ ExternalServicesModule:
        binds v1 AmazonSQS x2 (listener/sender), v1 AmazonS3;
        installs shared ParameterStoreModule + NetworkRetryerModule + ingestor JestModule
  IngestorApplication ─▶ IngestorModule: AsyncDispatcher, N x shared.SQSListener, ListenerManager, PollerJobProvider, Builders, Transformers
  shared: SQSClient/SQSListenerClient, S3WorkspaceService, AuthClient, Event/SNSNotification/Annotations,
          ErrorHelper, ConfigProcessingServerCommand, HealthCheckRegistrar  ─▶ AWS Java SDK v1 1.12.720 (AmazonSQS, AmazonS3)
  ingestor JestModule: DefaultAWSCredentialsProviderChain (v1) + vc.inreach.aws AWSSigner (v1) ─▶ JestClient (io.searchbox 6.3.1) ─▶ Elasticsearch/OpenSearch (AWS-signed REST)

AFTER — ingestor on commons + cloud-sdk (AWS v2)
  IngestorApplication ─▶ ExternalServicesModule:
        binds cloud-sdk MessagingClient[String] x2 (listener/sender configs), StorageClient (read);
        installs commons networkservices (AuthClient/FormatService/IntegrationProfile); installs JestModule (UNCHANGED v1 signer, §6)
  IngestorApplication ─▶ IngestorModule: appianway-commons AsyncDispatcher, N x SqsListener (cloud-sdk-api or wrapper), ListenerManager, PollerJobProvider, Builders, Transformers
  cloud-sdk-api: MessagingClient[T], QueueMessage[T], StorageClient, notification.workflow.{Event, Annotations, EventLogger}  ─▶ cloud-sdk-aws (SQS + S3 v2 impls) ─▶ AWS Java SDK v2 BOM
  appianway-commons: AsyncDispatcher/AbstractTask, ErrorHandler/ErrorHelper, health-indicator glue
  JestModule (UNCHANGED): vc.inreach AWSSigner + AWS v1 DefaultAWSCredentialsProviderChain (retained as-is) ─▶ JestClient (io.searchbox 6.3.1) ─▶ Elasticsearch/OpenSearch (AWS-signed REST) — v1 signer + a minimal AWS v1 auth jar coexist with the v2 SDK
```

## 4. Sequence — consume → transform → index

```
 1.  SqsListener (1 of N) ─▶ MessagingClient[String] (listener).receiveMessages(queueUrl, waitTimeSeconds=20, maxNumberOfMessages=10)
 2.  ─▶ List of QueueMessage[String]
 3.  SqsListener ─▶ AsyncDispatcher.submit(List, queueUrl) ─▶ IngestorTask.execute(List, queueUrl)
 4.  IngestorTask.getEventStoreMsgFromSNSMessage(): unwrap SNSNotification ─▶ List of Event
 5.  Builders/AttributeBuilder chain ─▶ List of TrackingMetaData (grouped by workflowId)
 6.  for each Event:
        ErrorTransformer.transform(event):
          if closeRun + failure status + no annotations yet:
            StorageClient.getContent(bucket, fileName) ─▶ error-file content (JSON)
            Annotations = parse(content); event.setAnnotations(Annotations)
 7.  ElasticSearchEventRepository.submitEvent(events, trackingMetaDataMap):
        Bulk.Builder(Index per event).build() ─▶ JestClient
        JestClient: AWS v1 SigV4 signing via vc.inreach AWSSigner (RETAINED as-is; X-G8)
        ─▶ signed bulk index request (txtrack-event-yyyy-MM-dd) ─▶ ES  (200; 409 ─▶ retry up to 3, exp. backoff)
        Update (upsert) per workflowId ─▶ txtrack-agg-yyyy-MM-dd (retry_on_conflict=5)
 8.  IngestorTask ─▶ MessagingClient[String] (sender/delete).deleteMessage(queueUrl, receiptHandle) per message
```

> Unaffected side-path (no AWS SDK): `com.coreoz.wisp.Scheduler` (`PollerJobProvider`) fires `DeleteExpiredIndex.deleteExpiredIndexes()` every 24h, calling `IndexESService` (`GetSettings`/`DeleteIndex` via the **same** `JestClient`) to purge `txtrack-agg-*`/`txtrack-event-*` older than 30 days (INT override; yaml default 90).

## 6. cloud-sdk / commons dependencies & assumed gaps

| Gap | Applies? | Detail |
|---|---|---|
| **S-G2** | **No** | ingestor's only S3 use is `getContent` (read) in `ErrorTransformer` — no write/copy, no metadata concern. |
| **W-G9** | **Yes — directly relevant.** | ingestor both **deserializes** `Event` off the wire (`IngestorTask.getEventStoreMsgFromSNSMessage`) **and mutates its `annotations`** before persisting (`ErrorTransformer.transform` calls `event.setAnnotations(...)` only when `event.getAnnotations() == null`). If an upstream producer already attached annotations and cloud-sdk-api's `Event` deserialization silently drops them (the W-G9.1 defect), ingestor's null-check would incorrectly re-derive them from the S3 error file, or the ES document would end up missing annotations that were sent. **ingestor must be gated behind the W-G9 fix landing in cloud-sdk-api**; the foundation round-trip corpus test should include a `closeRun` Event carrying annotations. |
| **X-G8** | **Yes — resolved by keeping v1.** | Jest + the `vc.inreach` v1 SigV4 signer stay **as-is** (AWS SDK v2 is incompatible with the Jest 6.3.1 / Apache HttpClient 4.x signing stack; mercury-services keeps the v1 pattern too). No cloud-sdk change; ingestor retains the v1 signer + a minimal AWS v1 auth jar. See §6.1. |
| **C-G6** | Optional | §5.3 composition works with it `private`. |
| **O-G1/O-G3** | N/A | ingestor keeps its own `AsyncDispatcher`/`ListenerManager`; no S3-event-parser. |

### 6.1 X-G8 — decision: keep the Jest v1 signer as-is (corrected)

**An earlier draft proposed migrating the Jest signer to AWS SDK v2 (a cloud-sdk `JestClientBuilder` or a local v2 `Aws4Signer` interceptor). That is wrong and has been dropped.** Jest `io.searchbox` 6.3.1 runs on Apache HttpClient 4.x and is signed by `vc.inreach.aws.request.AWSSigner` / `AWSSigningRequestInterceptor`, which are built against the **AWS SDK v1** `AWSCredentialsProvider`/SigV4 API. There is no drop-in v2 equivalent that plugs into that Jest/Apache-4 request path, and — verified across mercury-services — **no module migrates it**:

| mercury-services module | ES/Jest signing today |
|---|---|
| `visibility-inbound` | v1 `com.amazonaws.auth.AWS4Signer` + a copied `AwsRequestSigner` (aws-request-signing-apache-interceptor) |
| `oceanschedules` (loader, port-pair-generator) | `vc.inreach.aws.request.AWSSigner` + `AWSSigningRequestInterceptor` with `JestClientFactory` |
| `elasticsearch-purge` (lambda) | v1 `AWS4Signer` + `AWSRequestSigningApacheInterceptor` |

**Decision:** keep ingestor's `JestModule` wiring **unchanged** — `DefaultAWSCredentialsProviderChain` (v1) + `vc.inreach` `AWSSigner`/`AWSSigningRequestInterceptor` + `JestClientFactory`. This means ingestor must **retain a minimal AWS SDK v1 dependency** (the v1 `auth`/credentials classes + `vc.inreach:aws-signing-request-interceptor:0.0.16`) on its classpath, coexisting with the cloud-sdk-aws **v2** stack that handles SQS/S3. v1 and v2 SDKs live in different packages (`com.amazonaws.*` vs `software.amazon.awssdk.*`) and coexist without conflict; ingestor is the one module carrying both. `CreateMappingTemplate` is likewise unchanged. No cloud-sdk change is required for X-G8 at all.

> Net: the SQS/S3/network-services/config/event-model layers migrate to cloud-sdk v2 exactly like every other module; the **Elasticsearch/Jest signing layer alone stays on v1**, isolated inside `JestModule`.

### 6.2 What ingestor consumes

- **cloud-sdk-api:** `MessagingClient[String]`, `QueueMessage[String]`, `StorageClient` (read), `notification.workflow.Event`, `notification.annotation.Annotations`.
- **commons:** `ConfigProcessingServerCommand` (+ transforms), `networkservices.*` (`AuthClient`, `FormatService`, `IntegrationProfileByIdService` caches, parameter-store lookup), health base.
- **appianway-commons:** `Dispatcher`/`AsyncDispatcher` base (ingestor's orchestration stays module-local; only the `Dispatcher` contract + any shared base class move), `ErrorHandler`/`ErrorHelper`, `RecoverableException`, `InboundSqsHealthCheck` wrapper.
- **Nothing moves to appianway-commons that has a commons/cloud-sdk-api home** — `Event`, `Annotations`, `AuthClient`, network-services, config command all come from upstream.

## 10. Risks & mitigations

| Risk | Mitigation |
|---|---|
| **v1/v2 SDK coexistence** — ingestor keeps AWS SDK **v1** (for the Jest `vc.inreach` signer) on the same classpath as cloud-sdk-aws's **v2** SDK (X-G8, §6.1) | Different package namespaces (`com.amazonaws.*` vs `software.amazon.awssdk.*`) — no classloader conflict; scope the retained v1 jars to `aws-java-sdk-core` + `vc.inreach` only (not the full v1 SDK); assert no `NoClassDefFoundError` at boot for both profiles |
| Accidentally "upgrading" the Jest signer to v2 (the dropped Route A/B) breaks ES signing — Jest 6.3.1/Apache-HttpClient-4.x has no compatible v2 signer | Explicitly **do not** touch `JestModule`; the v1 signer stays (mercury-services visibility-inbound/oceanschedules/elasticsearch-purge all keep v1). Confirm a signed request still succeeds against the ES domain (INT smoke) |
| **W-G9** annotations round-trip defect silently drops `Annotations` ingestor is specifically responsible for attaching/preserving | Do not cut ingestor over until the W-G9 fix lands in cloud-sdk-api; add the ingestor-specific corpus case (closeRun event with annotations) to the foundation round-trip test |
| Redundant `WorkspaceService` binding (bound twice today) papers over a latent Guice binding-order bug; collapsing to a single `StorageClient` injection could surface it | Collapse deliberately during the rebind and run the full boot + smoke rather than mechanically translating both bindings |
| Two named `MessagingClient[String]` instances (listener vs sender/delete) must preserve the current `AWSClientConfiguration` split (independent timeouts/retry) | Map `sqs_listener` → listener-scoped config, `sqs_sender` → sender-scoped config explicitly; do not collapse unless verified identical |
| Jest/`io.searchbox` stays on the Java-17 reflective caller-lookup WARN (`sun.reflect.Reflection.getCallerClass`, already observed benign) | Cosmetic only, already tolerated on the DW5 baseline; no action, but don't mistake it for a new regression |
| `ce-ingestor` profile easy to forget in verification (same jar/yaml, only properties differ) | Explicit two-profile boot + smoke in §9 |
| `functional-testing`'s SQS/S3 fakes lag the cloud-sdk-api rebind, breaking ingestor's tests | Sequence ingestor strictly after `functional-testing`; do not start the rebind until the fakes are cloud-sdk-api-shaped |
