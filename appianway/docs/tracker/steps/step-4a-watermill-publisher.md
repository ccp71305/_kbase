# Step 4a — watermill-publisher (`WI01124532-aws-sdk-upgrade-watermill-publisher`)

← [Tracker home](../README.md) · [All steps](README.md) · [Step 4 plan](step-4-plan.md)

Cut 2026-11-20 from the feature branch at `36a14ced` (after PR #12). Design page: [watermill-publisher design](../../redesign/2026-10-30-apway-WI01124532-watermill-publisher.md). Existing defects named by the design (Risks): the DLQ redrive stops for good after one failed run (`scheduleAtFixedRate`); every stream reset starts another non-daemon `CleanerThread` that never stops; an SQS failure in `ResponseObserver.onNext` cancels the stream and clears every pending ack; `resetStream` is not volatile; `ListenerManager.stop()` stops neither the executors nor the gRPC channel; a poison message cycles DLQ ↔ pickup queue for ever.

**Baseline (2026-11-20, `36a14ced`):** watermill-publisher runs 153 tests, 0 failures, 0 skipped (`mvn -o -pl watermill-publisher clean test` in the build worktree, 1:14 min). 30 production classes; 6 import SDK v1 (`ExternalServicesModule`, `Task`, `TaskFactory`, `AsyncDispatcher`, `DeadLetterService`, `WatermillPubTask`) plus the load harness `task/Test.java` in main sources; 3 more use the `shared` v1 classes (`WatermillPubModule`, `StatusEventGrpcClient`, `ResponseObserver`). No functional test (the pom names `src/test/resources-functional`, which does not exist).

**What watermill-publisher does:** `listenerThreads` (2) listeners on the pickup queue (`inttra2_qa_sqs_watermill_ce`, visibility timeout 60 s, redrive to `_dlq` after 5 receives), each with its own synchronous dispatcher, task and **gRPC stream** (`StatusEventGrpcClient` is not a singleton). Per message: parse `MetaData`, read the status-event XML from the workspace (ISO-8859-1), XML → `ExportSEPartInt` → `ShipmentStatusChangeEvent`, `requestObserver.onNext` on the `publishShipmentStatusMicroBatch` stream (gzip, call credentials username / password / tenant). The message is deleted when the `PublisherAck` with its message id comes back (on the gRPC thread), or at once when the transform fails. Every 30 min (first run at start) `DeadLetterService` moves the DLQ's messages back to the pickup queue (body only) until 3 empty receives.

**AWS today (SDK v1):** `ExternalServicesModule` builds `AmazonSQS` ×2 (listener, sender), `AmazonS3`, `AmazonSNS` (bound, never used: no event is published) and installs `ParameterStoreModule(userIdKey, passwordKey)`; `ResponseObserver` reads the queue's `VisibilityTimeout` (the ack expiry) at each stream creation. No health check.

<a id="findings"></a>
**Findings while preparing (2026-11-20):**
- QA has traffic: `Processing workflowId` lines every day in `AppianWay-watermill-publisher-latest-qa`; the pickup queue was empty at the check.
- The v1 SQS fake answers `getQueueAttributes` with `null`; the golden test stubs `VisibilityTimeout` = 60 (QA's value) on the spy.
- No in-process gRPC transport in the local repository (`grpc-inprocess` not cached, builds are offline); the golden test runs a Netty gRPC server on a free localhost port (plaintext), and the test overrides only the `ManagedChannel` binding.
- The DLQ redrive counts **all** empty receives, not consecutive ones (stops after the 3rd empty one in total).
- Drain ([A28](../closed-items.md#a28)): each listener has its own synchronous dispatcher, so the drain is per dispatcher, as ingestor's. A batch is "done" only when its acks are back: the drain also waits for the stream's pending acks (else the sender client closes before the deletes and the messages are published again).

4. Full build, pre-review, PR; runtime test 10 (local against QA up to the publish call, [D48](../decisions.md#d48)).
